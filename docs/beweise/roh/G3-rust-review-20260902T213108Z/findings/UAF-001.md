## Description

`HandleRegister` stores live connection pipe handles as raw `isize` values so
that `stoppen()`, `kopplung_loesen()` and the watchdog thread can break a
blocking overlapped read with `CancelIoEx`. The register therefore keeps a
*non-owning* copy of a Win32 kernel handle that outlives no owner of its own —
its soundness rests entirely on one documented invariant, spelled out in the
`unsafe impl Send for HandleRegister` SAFETY comment at
`broker/src/transport/server_v3.rs:971`:

> „Das Register haelt sie nur, solange der besitzende Thread seinen
> `Verbindungsgriff` noch nicht fallen gelassen hat."
> (*the register holds them only as long as the owning thread has not yet
> dropped its `Verbindungsgriff`*)

i.e. **the register entry must always be removed before the handle is closed.**

On the normal path that invariant holds: inside `verbindung_bedienen` the
register token `_handle_eintrag` is the *first* body local
(`server_v3.rs:2275`) and the owning `Arc<Verbindungsgriff>` is a *parameter*,
so the token drops first and the `CloseHandle` in `Verbindungsgriff::drop`
runs afterwards.

On the `std::thread::Builder::spawn` **failure** path the ordering is inverted.
The acceptor registers the handle (`server_v3.rs:1911-1914`), builds the
`HandleEintrag` token, and then hands both to a `move` closure. When `spawn`
returns `Err`, nothing runs the connection function — the closure itself is
dropped, and its captured upvars drop in capture (declaration) order, not in
the order the invariant needs:

| upvar index | capture | effect on drop |
|---|---|---|
| 0 | `worker_platz` | releases the worker slot |
| 1 | `verzoegerung` | — |
| 2 | `id` | — |
| **3** | **`griff`** (`Arc<Verbindungsgriff>`, refcount 1) | **`CloseHandle(h)`** |
| 4…19 | `senke`, `kopplungen`, `handles`, `statistik`, `bv`, `be`, … | Arc decrements, one `Mutex` acquisition inside `griff`'s drop |
| **20 (last)** | **`handle_eintrag`** | **removes `(id, h)` from `HandleRegister`** |

Between upvar 3 and upvar 20 the register publishes a handle value that has
already been closed. Every reader of that register calls `CancelIoEx` on it
without any revalidation.

The `Err(_)` arm's own comment ("Closure-Drop gibt Workerplatz, Handle und
Register frei" — *closure drop releases worker slot, handle and register*)
names exactly this order and treats it as correct; it is the reverse of what
the `HandleRegister` SAFETY comment requires.

## Data flow

- **Source:** local unprivileged client connects to the pipe; the acceptor
  accepts it (`v3_server_starten_intern`, `server_v3.rs:1897`) and publishes
  the raw handle into `HandleRegister.offen` at `server_v3.rs:1913`.
  The attacker-influenced trigger is `std::thread::Builder::spawn` returning
  `Err` (thread/handle/memory exhaustion caused by connection churn plus other
  local load); the worker cap of `MAX_VERBINDUNGEN` bounds but does not
  eliminate that.
- **Sink:** `CancelIoEx(*h as HANDLE, ...)` in `alle_io_abbrechen`
  (`server_v3.rs:1289`), `io_abbrechen` (`server_v3.rs:1301`) and the watchdog
  thread (`server_v3.rs:1741`), all reached from `V3Griff::stoppen()`,
  `V3Closer::link_schliessen()` and the bootstrap-deadline sweep.
- **Validation:** none. The register stores a bare `isize`; no generation
  counter, no `is_null` check, no re-lookup against a live owner. The only
  protection is the drop-order invariant that this path violates.

## Reachability trace

`v3_server_starten_intern` → acceptor thread loop → `handle_uebernehmen` →
register push → `Builder::spawn` returns `Err` → closure drop
(`griff` → `CloseHandle`, … , `handle_eintrag` → deregister).

Concurrently, on other threads:
`V3Griff::stoppen` → `alle_io_abbrechen` → `CancelIoEx(stale handle)`
(`stoppen` runs this in a 5 ms polling loop, so it samples the window
repeatedly), and
`eqcop-v3-wachhund` thread → bootstrap-deadline sweep → `CancelIoEx(stale handle)`.

## Impact

A Win32 handle value that has been released back to the process handle table
stays published in a shared register and is used by other threads. Windows
recycles handle values aggressively, and the broker mints new handles
continuously on other threads during the window (`Ereignis::neu` →
`CreateEventW` per connection thread, `naechste_instanz` → `CreateNamedPipeW`,
SQLite store file handles, `File` opens in `persistenz`). If the value is
re-issued inside the window, `CancelIoEx` is applied to an unrelated kernel
object:

- cancelling a pending `ConnectNamedPipe` on a listener instance makes the
  acceptor treat the listener as failed (`listener_fehler`, fail-closed
  shutdown of the whole v3 endpoint — availability loss for all probes);
- cancelling I/O on a store file handle surfaces in SQLite as
  `ERROR_OPERATION_ABORTED` on a write/fsync, which the store reports as a
  degraded/IO error path;
- cancelling another live connection's read tears down a legitimate,
  authenticated probe connection.

This is a use-after-release of a kernel resource rather than a heap
use-after-free: it cannot corrupt the Rust heap, but it violates exactly the
ownership invariant the surrounding `unsafe` code documents, and the damage is
inflicted on whichever object inherits the recycled value. Reachability
requires a `spawn` failure, so this is a reliability/robustness-grade defect
under a local unprivileged attacker who can drive resource exhaustion, not a
one-shot exploit.

## Mitigations checked

- `// SAFETY:` comment at `server_v3.rs:971` names the exact invariant that is
  broken here; it is a claim, not an enforcement.
- No `debug_assert!` or runtime check ties register removal to handle closure;
  the two live in different `Drop` impls with no ordering relation.
- The tight `while !j.is_finished() { alle_io_abbrechen(...); sleep(5ms) }`
  loop in `stoppen()` (`server_v3.rs:1247`) *increases* the chance of sampling
  the window rather than mitigating it.
- `HandleEintrag::drop` uses `if let Ok(mut r) = self.register.lock()`, i.e. it
  silently skips removal on a poisoned mutex, while the acceptor's push uses
  `unwrap_or_else(|e| e.into_inner())` and recovers — the two halves of the
  same invariant do not agree on poisoning either.
- NAK-123's `tests/security_vectors.rs` covers start-failure paths
  (`V3StartTestFehler::*`) and worker-cap/name-ownership, but has no seam for a
  failed connection-thread `spawn`, so this path is untested.
- No MIRI, no sanitizer, no `#![deny(unsafe_op_in_unsafe_fn)]`, no `[lints]`
  table in `broker/Cargo.toml`; `debug_assertions` are stripped in release.

## Recommendation

Do not rely on closure-upvar drop order for a safety invariant. Either

1. drop the register token explicitly before the handle owner in the failure
   arm — restructure so the closure returns the token, or wrap both in one
   struct whose `Drop` performs deregistration *then* `CloseHandle`:

   ```rust
   struct RegistrierterGriff {
       eintrag: HandleEintrag,          // removed first
       griff: Arc<Verbindungsgriff>,    // closed second
   }
   ```
   (field declaration order then encodes the invariant the comment states), or

2. make the register self-validating: store `Weak<Verbindungsgriff>` (or the
   `Arc` itself) instead of a bare `isize`, so `alle_io_abbrechen` can only
   `CancelIoEx` a handle whose owner is provably still alive.

Additionally, align the poisoning behaviour: `HandleEintrag::drop`,
`alle_io_abbrechen` and `io_abbrechen` should all use
`unwrap_or_else(|e| e.into_inner())` like the acceptor does, so a poisoned
register cannot leave stale entries behind.
